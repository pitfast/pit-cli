# PitFast Commerce Demo

`pitstop-demo` is a small, runnable application fixture rather than a
placeholder workload:

- `web/` is a React/Vite static-web frontend.
- `orders/` is a Go `net/http` service using `pgx` to persist real orders in
  PostgreSQL.
- `users/` is a Python ASGI service kept dependency-light for the current
  componentize-py adapter.
- `app.pit` deploys all services behind one PitLane listener.

The database is an external Docker PostgreSQL container. PitLane owns the
resource gateway and injects only a gateway URL into the guest; provider
credentials are not put in the manifest or WASM artifact.

## Local setup

Prepare PostgreSQL once (the script is idempotent and only manages the
container named `pitfast-postgres-demo`):

```bash
./scripts/demo-postgres.sh
```

The current local demo container uses a host-bridge trust rule for the
gateway path and a dedicated `pit` role, so the backend password never enters
the guest. This is a local demonstration setup, not a production PostgreSQL
authentication policy.

From this directory:

```bash
./scripts/demo-build.sh
./scripts/demo-start.sh
curl http://127.0.0.1:7080/orders/health
curl -X POST -H 'Content-Type: application/json' \
  --data '{"customer":"BukuWarung","amount":125000}' \
  http://127.0.0.1:7080/orders
curl http://127.0.0.1:7080/orders
```

Open the frontend at `http://127.0.0.1:7080/` and watch executions with the
release-built `pit cockpit` command. Stop only the demo-owned PitLane process
with `./scripts/demo-stop.sh`.

`PITFAST_DEMO_DATABASE_URL` may override the host-side provider URL. The URL
must be reachable by the PitLane host process; it is not copied into guest
environment state except for the gateway URL generated by PitLane.

## Mixed million-request burst

The regular demo burst exercises CPU work. For a large mixed arrival test
that also performs PostgreSQL reads and writes, run:

    ./scripts/demo-burst-million.sh --requests 1000000 --concurrency 64

This generates one million total arrivals. By default one request per 1,000
is a PostgreSQL order write, while the remaining traffic mixes PostgreSQL
reads, database health checks, user health checks, and small user work.
Concurrency is bounded so the load generator does not allocate one million
threads or sockets. This is not a claim of one million simultaneous
connections.
